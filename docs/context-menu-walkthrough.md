# Context menu walkthrough

Right-clicking a node — on the canvas or in the layers panel — now opens a menu with Duplicate, Delete, Group, Ungroup, Create Component, Bring to Front, and Send to Back, each enabled or disabled based on the current selection. Before this, every one of those actions except Delete/Group/Ungroup/Create Component didn't exist at all (no Duplicate, no z-order control), and the four that did exist were keyboard-only.

## Why this needed a refactor before it needed a menu

Delete/Group/Ungroup/Create Component were inline blocks inside `useKeyboardShortcuts.ts`'s single `handleKeyDown` closure — not standalone functions anything else could call. Duplicating that logic into a second place (the menu) would have meant "what does Delete actually do" living in two spots that could silently drift apart. So the first move was extracting all of it, verbatim, into `apps/web/src/canvas/selectionActions.ts` — `deleteSelection()`, `groupSelection()`, `ungroupSelection()`, `createComponentFromSelection()`, later joined by `duplicateSelection()`, `bringToFront()`, `sendToBack()`. `useKeyboardShortcuts.ts`'s handlers collapsed into one-line calls into these; the context menu calls the exact same functions. There's now exactly one place that knows what each action does, and the keyboard shortcut and the menu item can never disagree about it.

## Two new Commands

**`DuplicateNodesCommand.ts`** clones each selected top-level member (plus its descendants, via the existing `collectWithDescendants`) *under the same parent* as the original — deliberately not reusing `componentMutations.ts`'s clone helpers, which reparent everything under a brand-new synthetic root and therefore need a coordinate-space conversion this doesn't. Each clone is offset by a fixed `DUPLICATE_OFFSET = 16` and spliced into its parent's `children` array immediately after the original, rather than appended to the end the way `addNodeToGraph` always does — so a duplicate visually "belongs" right next to what it was copied from. That fixed offset turns out to matter only for an absolutely-positioned node; a flex flow child's `x`/`y` gets overwritten by the very next `resolveFlexLayout` pass based on its new index in the children array, regardless of what offset was applied — no special-casing needed, verified live (a duplicated flex child landed at its flex-resolved position, not the raw +16). `invert` reuses the existing `removeNodesFromGraph`.

**`ReorderToEdgeCommand.ts`** implements both Bring to Front and Send to Back as one function, `createReorderToEdgeCommand(graph, nodeIds, edge)`. A multi-selection can span different parents, so it groups the selected ids by parent and rebuilds each parent's *entire* `children` array in one shot — `rest` (everything not selected, order preserved) and `moved` (the selected ones, their own relative order preserved) concatenated in the edge's direction — rather than calling the existing `reorderChildInGraph` once per node sequentially. That was a deliberate simplification made mid-implementation: a sequence of single-node reorders means each move's target index depends on where the previous move left things, which gets fragile fast once more than one node is involved. Direct array reconstruction has no such ordering dependency. An `arraysEqual` check skips emitting a command at all if the result would be a no-op (everything already at the requested edge).

Both commands needed `hasAncestorAmongMembers` (graph.ts) — "is one selected node an ancestor of another selected node" — which was already duplicated privately in `GroupNodesCommand.ts` and `componentMutations.ts`. Exported one shared copy from `graphMutations.ts` instead of writing a third private copy; the two existing call sites were updated to import it.

## Base UI already had what this needed

Before writing anything, the actual question was whether Base UI ships a context-menu primitive at all, or whether the app would need to hand-roll positioning/portal/click-outside logic. It does — `@base-ui/react/context-menu`, and inspecting its type definitions confirmed its `Portal`/`Positioner`/`Popup`/`Item`/`Separator` parts are literal aliases of the `Menu` primitive's own same-named parts. That meant the existing `.menu-popup`/`.menu-item`/`.menu-positioner` CSS (already written for the toolbar's dropdown menus) applies to a context menu completely unchanged — the only new CSS needed was two small states for the parts the toolbar menus never used: `.menu-item[data-disabled]` and `.menu-separator`.

## One shared component, not two

**`NodeContextMenu.tsx`** is self-contained the same way `SelectionOverlay`/`FlexInsertionIndicator` already are — it reads `useSelection()`/`useSceneGraph()` itself to decide what's enabled, and calls straight into `selectionActions.ts` on click, rather than having seven callback props threaded down into it. It wraps whatever `children` it's given via `ContextMenu.Trigger`, and takes one small prop the two call sites genuinely need different values for: `onContextMenu`, run on the raw right-click *before* the menu computes its enabled state — the one thing that's actually different between "right-clicked the canvas" (needs to hit-test which node was clicked) and "right-clicked a layers-panel row" (already knows its own node).

- **Canvas** (`Canvas.tsx`): the whole `<canvas>` element is wrapped in `NodeContextMenu`. `handleContextMenu` hit-tests the click point (`hitTestScene`, the same helper `handleDoubleClick` already uses) and, if it hit a node not already part of the current selection, replaces the selection with just that node — matching how right-click works in every other design tool. Right-clicking a node that's already part of a multi-selection leaves the selection untouched, so the menu applies to the whole set. Right-clicking empty canvas leaves whatever was selected alone and the menu still opens, with every item correctly disabled — simpler than fighting Base UI's own open-on-contextmenu behavior to suppress it for that one case.
- **Layers panel** (`LayerItem.tsx`): the `.layer-row` div is wrapped in `NodeContextMenu`, with `onContextMenu` selecting that row's node only if it wasn't already selected — identical semantics to the canvas, reusing the row's own existing `onSelect` callback.

## What's deliberately out of scope

- **Cut/Copy/Paste** — needs its own design (in-app clipboard vs. OS clipboard, where a paste lands, whether it works across pages), not something to bolt onto this menu as an afterthought.
- **A menu for right-clicking empty canvas space** — there's nothing to put there without Paste; the canvas menu still opens on an empty-space right-click today, just with everything disabled, rather than being suppressed entirely.

## Verified live

Canvas right-click on an unselected node (selects it, menu shows correct enablement) and on already-selected empty space (Group/Ungroup correctly disabled); Duplicate via the menu (clone correctly spliced in next to the original, correctly flex-reflowed, not at the raw offset) with undo restoring the exact prior graph; multi-select via layers-panel shift-click → right-click → Group (creates the group, enabled correctly) with undo restoring the original ungrouped members; layers-panel right-click on an unselected row (selects it first, then shows the menu); Send to Back (moves to index 0 in the parent's children array, reflows visually) with undo restoring the original order. Zero console errors across the whole pass.

One pre-existing quirk surfaced during this verification, not introduced by it: undoing an action that reselects a *newly created* node (Duplicate, Group, Create Component) used to leave a stale selection id pointing at a node that undo had just removed, showing a phantom "N objects selected" instead of a clean empty state — because undo/redo Commands never touched `selectionStore` at all. Fixed separately (see the "stale selection after undo" note in `pagesStore.ts`'s `createPage`, which now prunes both `selectedIds` and `hoveredId` reactively on every scene change, virtual-id-aware for component-instance children selected via the layers panel).
