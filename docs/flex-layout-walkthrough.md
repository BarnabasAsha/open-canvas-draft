# Flex layout walkthrough

Every node used to be positioned by hand-set `x`/`y`/`width`/`height` — intuitive for free-form dragging, but a Frame or Section had no notion of "stack these children with a gap." This adds that, opt-in per container, Figma-style: a Frame or Section's layout defaults to `layoutMode: "none"` (today's exact free-placement behavior, byte-for-byte), and flipping "Auto layout" on in the properties panel turns it into a flex container that arranges its own flow children. Group is deliberately excluded — its box is never something you set, so it stays outside the layout system entirely.

## Why nothing in rendering, hit-testing, or selection needed to change

The codebase already had the shape this needed: `reconcileGroupBounds.ts` recomputes a Group's bounds and writes them straight back into the graph after every mutation, via a wrapper in `createSceneStore.ts`. Rendering, hit-testing, `selectionBounds.ts`, and resize handles all read a node's `x`/`y`/`width`/`height` directly off the stored object with zero notion of who last set those values.

So flex layout follows the same precedent instead of inventing a parallel "resolved subtree" system (the way `resolveInstance` handles component instances): a second pass, `resolveFlexLayout`, runs right after `reconcileGroupBounds` on every write —

```ts
function update(updater: (graph: SceneGraph) => SceneGraph): void {
  store.update((graph) => resolveFlexLayout(reconcileGroupBounds(updater(graph))));
}
```

Order matters — groups settle first, so a flex container that happens to hold a Group measures against that Group's already-current bounds, not a stale one. Once flex-resolved values are written into the real nodes, every downstream system keeps working completely unchanged. The same `resolveFlexLayout(reconcileGroupBounds(initial))` call also seeds a page's *initial* state (`createSceneStore.ts`), so a page loaded straight from seed data or a saved document doesn't need hand-computed positions baked in — it only needs the right structure (children arrays, `layoutMode`, sizing modes), and the real geometry resolves before the first paint.

## The schema: per-child fields on every node, container fields on Frame/Section only

`baseNodeShape` (`packages/schema/src/index.ts`) gains three fields every node type carries, since any node could end up inside *someone's* flex container:

```ts
sizingHorizontal: SizingModeSchema,  // "fixed" | "hug" | "fill"
sizingVertical: SizingModeSchema,
positioning: PositioningModeSchema,  // "flow" | "absolute"
```

`FrameNodeSchema`/`SectionNodeSchema` additionally get the container-level fields — `layoutMode` (`"none" | "flex"`), `direction` (`"row" | "column"`), `gap`, `padding` (a full `{top, right, bottom, left}` box, matching CSS, even though v1's UI only exposes one linked "Padding" field that writes all four sides at once — avoids a later breaking schema migration once per-side control is added). `GroupNodeSchema` gets none of this. Every field is required, no `.default()` — matching this file's existing convention that every construction site is an explicit literal, so every Frame/Section/shape-creation call site (`frameTool.ts`, `sectionTool.ts`, `nodeFactories.ts`, `seedData.ts`, `componentMutations.ts`) needed updating to spell out the new defaults (`layoutMode: "none"`, `sizingHorizontal: "fixed"`, etc.) rather than silently inheriting them.

## The algorithm (`packages/commands/src/flexLayout.ts`): two passes, because nested hug needs bottom-up sizing first

A flex frame that's itself set to "hug" and contains another flex frame that's *also* "hug" can't be resolved top-down in one sweep — the outer frame's own size depends on knowing the inner frame's natural size first, which depends on *its* children. So resolution happens in two distinct passes.

**Pass 1 — `measureNaturalSize`, bottom-up, memoized.** "What size would this node need to be if something hugged it?", independent of whether its actual parent uses that value. For a non-flex node (a `"none"`-mode frame, a Group, a leaf shape), natural size is just its own currently-stored width/height — its size is manually managed. For a flex container, natural size is the sum of its flow children's natural main-axis sizes plus gaps and padding, and the max of their cross-axis sizes plus padding — recursing into each child. Absolute children (`positioning: "absolute"`) are excluded entirely from this sum, same as they're excluded from placement in Pass 2. A `"fill"`-sizing child is measured exactly like `"fixed"`/`"hug"` here (its *current stored* size) — which is what makes `"fill"` safely inert inside a `"hug"` parent later with zero special-casing: nothing about fill's actual runtime behavior (distributing leftover space) matters to the parent's own measurement.

Measurement is lazy, not a separate eager pass over the whole graph — `measureNaturalSize` is called from inside Pass 2, only for the subtrees Pass 2's own placement actually reaches, so cost stays proportional to how much of the graph is flex-relevant rather than total node count (this was a code-review fix; the first draft ran an unconditional full-graph pass).

**Pass 2 — `placeFlexChildren`/`placeSubtree`, top-down, pre-order.** Given a container's own already-resolved final size (its current stored size at the root of a traversal, or whatever its parent's own placement pass just assigned it), each flow child's final size on each axis resolves per its sizing mode: `"fixed"` keeps its current stored value, `"hug"` uses the Pass-1 natural size, `"fill"` gets an equal share of whatever main-axis space is left after every non-fill child and all gaps are subtracted. Children are then walked in order along the main axis, positioned per `primaryAxisAlign` (`start`/`center`/`end`/`spaceBetween`, all computed from one shared `leftover` value), and per-child on the cross axis per `crossAxisAlign` — with one CSS-matching rule: `"fill"` always occupies the full cross extent regardless of alignment, `"hug"` under `crossAxisAlign: "stretch"` also fills (mirroring `align-items: stretch` only affecting children with no explicit size), and `"fixed"` never stretches, an explicit size always wins. Absolute children are left completely untouched by both passes. Once a flow child's own size is resolved, `placeSubtree` recurses into it — so a nested flex container's children are only placed once its own final box is actually known, never before.

A small subtlety worth calling out: line/arrow nodes don't have meaningful width/height — their geometry is `x`/`y`/`x2`/`y2` (see `resizeMath.ts`'s own comment on this same point). Flex treats them as always `"fixed"`-size (`isFixedGeometry`), only ever repositioning them by shifting `x2`/`y2` by the same delta as `x`/`y` (`applyResolvedGeometry`), never resizing them via hug/fill.

## Wiring it into interaction: two things had to change for flex to feel native, not bolted on

Writing resolved values into the graph made rendering/selection/undo work for free, but two *interactions* still assumed the old "position is just wherever the user last dragged it" model, and both needed deliberate handling.

**1. Dragging a flex child out of its container, or reordering within one.** Without intervention, `resolveFlexLayout` — wired into every single `sceneStore.update()` — would snap a flow child straight back to its flex-computed slot on the very next pointermove, so a drag could never actually move it anywhere; `findContainerAt` would keep re-detecting the same parent forever. `selectTool.ts`'s `MoveDrag` state now tracks `flexOverrides` (which dragged nodes started as flow children of a flex-mode parent) and forces those nodes to `positioning: "absolute"` — but only once the drag has genuinely crossed a movement threshold (`hasCrossedThreshold`, see the bug section below), never on a bare click. `commitMove` restores `positioning: "flow"` once the gesture settles (`restoreFlexPositioning`), so the override is purely transient — a purely internal implementation detail of "how do I let this node's write stick for the duration of one drag," invisible in the undo history.

Reparenting itself (`reparentDraggedNodes`) additionally checks whether the *target* container is flex-mode: if so, `findFlexInsertionIndex` (`flexInsertion.ts`) projects the drag point onto the container's main axis against its flow children's current midpoints, returning both an insertion index and a scene-space line for a live indicator (`flexInsertionStore` + `FlexInsertionIndicator.tsx`, both new, mirroring the existing `marqueeStore`/`SelectionOverlay` pattern), and `sceneStore.reorderNode(id, targetParentId, index)` is called instead of a plain append-only `reparentNode`. That needed a new graph primitive — `reparentNodeInGraph` always appended and no-op'd on same-parent moves, so `reorderChildInGraph` (`graphMutations.ts`) was added alongside it: same parent-cycle validation, but always splices into the target's `children` at a given index (clamped, or appended if omitted), including same-parent reordering, which the old function couldn't express at all.

**2. Manually resizing a hug/fill child.** Dragging a resize handle on a child whose sizing is `"hug"` or `"fill"` would otherwise get immediately overwritten by the very next `resolveFlexLayout` pass — the resize would visually flash and then snap back. `fixedSizingForHandle` (shared by both the single-node and group-resize paths in `selectTool.ts`) flips `sizingHorizontal`/`sizingVertical` to `"fixed"` on whichever axis the grabbed handle actually touches (via the existing `HANDLE_AXES` map), but only if the node's parent is a flex container. `ResizeDrag` carries both the true pre-drag node (`startNode`, used only for `commitResize`'s undo snapshot) and this flipped copy (`resizeBaseNode`, what every pointermove actually resizes from) — so the flip sticks for the whole gesture, live reconciliation naturally reflows siblings as you drag (matching Figma's own feel), and undo still correctly restores the original sizing mode, not just the position/size. `GroupResizeDrag` needed the identical split (`resizeBaseSnapshots` alongside `snapshots`) for multi-select/group resize — a code-review finding; the first draft only handled single-node resize, so a hug/fill member of a group resize would still snap back mid-gesture.

## Properties panel: two new sections, gated on context

**`LayoutSection.tsx`** — shown for a selected Frame/Section, single-selection only (batch-editing layout across a mixed multi-select isn't well-defined, same reasoning `PositionSection` already used). An "Auto layout" checkbox toggles `layoutMode` directly (mirroring Figma's binary affordance rather than a `none`/`flex` dropdown); when on, direction/gap/padding/alignment controls appear. The two alignment selects are labeled **"Justify content"** and **"Align items"** — deliberately the real CSS terms, not an invented "Align (main)"/"Align (cross)" pairing that was tried first and immediately turned out more confusing than the thing it was trying to simplify.

**`FlexChildSection.tsx`** — shown for a node whose *parent* is a flex-mode container, letting it declare `positioning` (flow/absolute) and, when flowing, `sizingHorizontal`/`sizingVertical`. `sizingOptionsFor` restricts what's offered: a Group only ever gets "Fixed" (offering hug/fill would silently do nothing, since `reconcileGroupBounds` re-fits a Group's bounds every cycle regardless of what a flex parent assigns it — see the "Group stays outside layout" note above), and "Hug" is hidden for any leaf node with no children to derive a size from. Needing the *parent* node is why `PropertiesPanel` gained a `parentNode` prop (looked up in `App.tsx` alongside the existing single-selection lookup) — previously it only ever needed the selected node itself. Both sections are skipped entirely for a virtual (component-instance-child) selection, matching the existing `isInstanceChild` guard already used to hide the Align section for the same reason: editing a definition's internal layout through an instance isn't supported yet.

`PositionSection.tsx` also got a smaller, related fix: its X/Y/W/H number fields used to silently accept and discard edits on an axis flex actually controls (e.g. typing a width into a `"hug"` child, which the next reconciliation pass would immediately overwrite). It now disables the corresponding field (`flexControlled`/`widthFlexControlled`/`heightFlexControlled`, computed from the parent's `layoutMode` and the node's own sizing mode) instead of silently eating the input.

## Bugs found and fixed along the way

**Undo only reverted the edited field, not flex's side effects.** Toggling "Auto layout" on, then Cmd+Z, restored `layoutMode` but left every child exactly where flex had just placed them — because `useNodeEdit.ts`'s undo snapshot (`beforeRef`) only captured the *one* node being edited, not the whole graph. Turning on layout mode is a single field edit that can move a dozen other nodes as a side effect of the very same `sceneStore.update()` call; undoing has to revert all of them, not just the field that triggered it. Fixed by snapshotting/diffing the entire `nodes` record instead of one node, and using `createSetNodesCommand` (plural) instead of `createSetNodeCommand`.

**Clicking a node scattered the whole layout, with no drag at all.** Reported live, with screenshots showing a headline jumping position on a bare selection click. Root cause: `applyMove` had zero drag-distance threshold — a real click's natural sub-pixel pointer jiggle between pointerdown and pointerup still fires at least one pointermove with a nonzero (if tiny) delta. That used to be harmless (an imperceptible nudge on an absolutely-positioned node), but became a visible, discrete reshuffle for a flex child, since even a 1px nudge can cross the midpoint between two siblings and trigger `findFlexInsertionIndex` to reorder them. Fixed with `MOVE_DRAG_THRESHOLD_PX = 3` (screen pixels, zoom-adjusted) — `applyMove` now bails out entirely until total pointer movement crosses that threshold, gated by a `hasCrossedThreshold` flag on the drag state, so a plain click never mutates the graph at all. This was the same root cause behind a second symptom reported in the same message — multi-select-then-group appearing broken, because the spurious reorder from the jiggle was silently changing what was structurally "selected" underneath the user. Verified live by simulating a 1px jiggle across five separate clicks: stable layer order confirmed, multi-select + Cmd+G group confirmed working.

**A no-op guard was missing on `reorderChildInGraph`.** Without one, dragging a node and releasing it in the exact position it started (a common, essentially-idle gesture) still recorded a full undo entry, since the function always spliced the array even when the result was identical. `isNoOpReorder` checks whether the clamped target index actually differs from the node's current index before doing anything, matching the existing `reparentNodeInGraph` convention of no-op'ing rather than mutating when nothing would actually change.

**Duplicated `transformPoint` across three-plus files.** `flexInsertion.ts` needed to convert a container-local insertion-line coordinate back into scene space, which turned out to be the same operation `sceneCorners.ts` and `resizeHandles.ts`/`resizeMath.ts` already each had their own private copy of. Consolidated into one `transformPoint(matrix, point)` in `worldTransform.ts`, all four call sites updated to import the shared version.

## Seed data now demonstrates the feature

`seedData.ts` was restructured around a flex hierarchy instead of hand-placed absolute coordinates: a root `"Hero"` frame (flex column, gap 80, padded) containing a `"Nav"` row (space-between, center-aligned, fills width, hugs height) and a `"Content"` row (gap 64, center-aligned) whose two children are a nested `"Copy"` column (flex, hugging both axes — eyebrow/headline/subhead/CTA stacked with a gap) and an unchanged fixed-size `"Hero Image"` frame. This is deliberately the same visual result the old hand-positioned seed data produced, just now expressed as a layout a person could actually reconstruct by hand in the UI, rather than as coordinates nobody but the algorithm understands.

## What's deliberately out of scope

- **CSS Grid** — a natural sequel once flex is proven out, not attempted here.
- **Flex-wrap** — every flex container is single-line/single-column; no wrapping behavior exists.
- **Layout inside saved component definitions** — a component definition's internal structure doesn't currently expose layout editing through an instance.
- **Text auto-resize / "hug contents" text measurement** — a related but separate feature (measuring a text node's own natural size from its actual rendered content) planned for later; today a text node's "hug" size is just whatever's currently stored on it, same as any other leaf.
- **Rotation** — both `reconcileGroupBounds`'s auto-fit and `resolveFlexLayout`'s placement assume a container's own rotation is 0, the same simplification `reparentNodeInGraph`/`translateNode` already made. Nothing currently lets a container be rotated, so this hasn't bitten yet — same category of gap as the line/arrow reparenting bug from the grouping work: correct until the first caller that actually exercises it.
- **Per-side padding UI** — the schema already stores a full 4-value box; the panel only exposes one linked field today.
