# Zoom and pan walkthrough

Scroll to pan, Ctrl/Cmd+scroll to zoom — plus everything that had to change to make that actually *correct*, not just visually present.

## The surprise: half of this already existed

`viewportStore` (`{ pan: {x, y}, zoom }`) has existed since Phase 2. `screenToScene`/`sceneToScreen` in `utils/coordinates.ts` already read it on every pointer event. `SelectionOverlay.tsx` and `TextEditOverlay.tsx` already called `sceneToScreen`/`getScreenTransform` for every outline, handle, and the text-edit `<textarea>`'s position and font size. None of that code was wrong — it was just never *exercised*, because nothing ever changed `viewportStore` away from its initial `{pan: {x:0,y:0}, zoom:1}`. The one piece that was missing, and the reason zoom looked completely absent rather than just unreachable, is that the canvas's own raster rendering (`drawScene.ts` / `Canvas.tsx`) never consulted the viewport at all — it always drew at a fixed 1:1 scale regardless of what `viewportStore` said.

That split — half the app already viewport-aware, half of it not — is what made this a surprisingly contained fix rather than a rewrite. Once rendering caught up, selection, dragging, resizing, text editing, and the properties panel all kept working at any zoom level with zero changes, because they'd already been built against the `screenToScene`/`sceneToScreen` conversion layer instead of raw pixel coordinates.

## Making the canvas actually render the viewport

**`canvas/renderer/drawScene.ts`** now takes a `viewport` argument. The background fill still happens first, in plain device-pixel space (`ctx.clearRect`/`fillRect(0, 0, width, height)`) — that has to cover the *full visible area* exactly once regardless of zoom, so it runs before any transform is applied. Then `ctx.save()`, `ctx.translate(pan.x, pan.y)`, `ctx.scale(zoom, zoom)`, draw every node, `ctx.restore()`. Content pans and scales; the page underneath it doesn't.

**`canvas/Canvas.tsx`** now subscribes to `viewportStore` the same way it already subscribed to `sceneStore`/`documentStore` — any pan/zoom change triggers a redraw through the same `render()` closure. The new piece is the wheel handler, and it's deliberately a *native* `addEventListener("wheel", handler, { passive: false })` inside the existing effect, not React's `onWheel` prop. Browsers can treat wheel listeners as passive by default, which would silently swallow `preventDefault()` — and without that, Ctrl+scroll would fall through to the browser's own page-zoom instead of ours, which is exactly the failure mode `preventDefault` exists to stop.

Plain scroll pans (`panBy`); Ctrl+scroll zooms (`zoomAtPoint`). Checking `e.ctrlKey` covers two gestures with one branch — trackpad pinch is delivered by the browser as a wheel event with `ctrlKey` set, the same signal it uses internally for its own pinch-to-zoom, so an explicit Ctrl/Cmd+scroll and a real pinch both land here without needing separate handling.

**`canvas/viewportControls.ts`** (new) holds the pure math: `panBy(viewport, dx, dy)` and `zoomAtPoint(viewport, screenPoint, factor)`. The zoom function keeps the scene point currently under `screenPoint` fixed on screen — `newPan = screenPoint - scenePoint * newZoom` — which is what makes zooming feel anchored at the cursor instead of always scaling from the origin. `MIN_ZOOM`/`MAX_ZOOM` (0.05–8) live here too, shared by both the wheel handler and the keyboard shortcuts below.

## The hit-testing radius that was already flagged

`resizeHandles.ts` had this comment sitting on `HANDLE_HIT_RADIUS` since Phase 3: *"Scene-unit hit radius. Fine while zoom is fixed at 1; once zoom/pan interaction exists this should scale with 1/zoom to stay a constant screen-pixel target."* That prediction was exactly right and exactly due — a fixed 8-scene-unit radius is a comfortable ~8 screen pixels at 100% zoom, but at 17% zoom it shrinks to barely 1 screen pixel (unclickable), and at 800% it balloons to 64 (absurdly oversized). `hitTestHandles` now takes a `zoom` parameter and divides the radius by it; `groupResize.ts`'s `hitTestGroupHandles` got the identical fix for multi-selection. `selectTool.ts` reads `viewportStore.getState().zoom` at the four call sites (both handle-hit-test checks in `onPointerDown`, both in `updateHoverState`) and threads it through.

Everything else that does scene-unit distance math — `MIN_DRAG_FOR_HANDLE` in the pen tool, `MIN_DRAW_SIZE` in `dragToCreateTool.ts` — has the same theoretical exposure (a tiny screen-space jitter maps to a larger scene-space distance at extreme zoom-out) but wasn't touched. Resize handles are a core, constant interaction every session touches; those thresholds are edge cases (tiny accidental drag at 5% zoom) that didn't seem worth the extra surface area in the same pass. Worth another look if it turns out to matter in practice.

## Keyboard shortcuts and the zoom indicator

**`useKeyboardShortcuts.ts`** adds Cmd/Ctrl+0 (reset to `INITIAL_VIEWPORT`, now exported from `viewportStore.ts` so both the shortcut and the indicator's reset button can reuse the exact same literal) and Cmd/Ctrl +/− (step zoom by ±20%, via `zoomAtPoint`). Keyboard zoom has no cursor position to anchor to the way the wheel handler does, so it anchors at the center of the currently-visible canvas instead (`canvasSizeStore.getState()`, halved).

**`ui/ZoomIndicator.tsx`** is a small presentational button, bottom-left of the canvas, showing `${Math.round(zoom * 100)}%`, click to reset. First version was always visible; changed after you pointed out it doesn't need to be — it should only show up while zooming is actually happening.

That "show only while active" behavior needed a timer reacting to `zoom` changes over time, which is a `useEffect` by nature — and this project's presentational-component rule is no `useEffect`, full stop. So the timing logic isn't in `ZoomIndicator` itself; it's `canvas/useZoomIndicatorVisible.ts`, a hook called from `App.tsx` (the container), which passes the resulting `visible: boolean` down as a plain prop. `ZoomIndicator` stays exactly what a presentational component should be — it doesn't know *why* it's visible, just that it is. Visibility is opacity + `pointerEvents`, not a conditional unmount: a CSS fade reads as more polished than a hard pop, and toggling `pointerEvents` means the invisible button doesn't sit there stealing clicks meant for the canvas underneath it.

## Two bugs, both caught by actually testing it

**Zoom sensitivity, way too hot.** First pass used `zoomFactor = Math.exp(-deltaY * 0.01)`. A single Playwright-synthesized wheel event with `deltaY: -400` instantly zoomed from 100% to the 800% clamp — one gesture, full range, no gradient at all. The bug wasn't the formula's shape, it was the coefficient: a real mouse-wheel notch delivers `deltaY` around 100, and a real trackpad delivers a stream of small per-frame deltas, both very different from one large synthetic jump. Dropped the coefficient to `0.002` — a single wheel notch now steps to about 82% of the previous zoom, and continuous trackpad scrolling feels smooth rather than twitchy. Re-verified by replaying the gesture as several small deltas instead of one big one, which is what actually exposed the difference — the first test had accidentally been testing the clamp, not the sensitivity.

**The indicator was visible on page load, before anything had zoomed.** `useZoomIndicatorVisible`'s first version tracked a `hasMounted` ref and skipped showing the indicator "on the first effect run." That's not the same thing as "on mount" under React 18 `StrictMode` (which this app has had since `main.tsx` was written): in development, `StrictMode` deliberately runs every effect twice on mount — once, clean up, then again — specifically to help surface effects with missing or incorrect cleanup. The `hasMounted` flag correctly ignored the *first* invocation, then read the *second, replayed* invocation as a genuine change and showed the indicator. The fix was to stop asking "have I run before" and instead ask "is this value different from last time" — a `previousZoom` ref compared against the current `zoom` on every effect run. `StrictMode`'s replay passes the identical `zoom` value both times, so the value-comparison version correctly sees no change either time, while still catching every *real* change exactly once. Confirmed by sampling the indicator's computed `opacity` at idle (0), immediately after a zoom tick (mid-fade), through the 1.2s linger window (1), and after it (0).

## Ranked, tersely

1. **The `StrictMode` double-invoke bug** — not hard to fix once understood, but the kind of thing that's invisible unless you specifically test the "did nothing happen yet" state, which is easy to skip when the feature obviously works once you interact with it.
2. **Zoom sensitivity** — the formula was always correct; the constant was wrong by roughly 5x, and the only way to feel that was to actually replay a realistic gesture instead of one synthetic extreme.
3. **The wheel listener's passive-by-default trap** — easy to miss entirely until Ctrl+scroll visibly zoomed the whole browser page instead of the canvas.
